# Pulsemetry IA (정보구조)

화면 · 메뉴 · 경로에 대한 판단이 엇갈릴 때는 이 문서를 기준으로 한다.

---

## 0. 문서 정보

| 항목 | 내용 |
| --- | --- |
| 문서명 | Pulsemetry IA (정보구조) |
| 적용 범위 | MVP 웹 대시보드 + 일반 사용자 온보딩 경로 |
| 상태 | 확정. 잔여 미확정은 9장 |

## 1. 이 문서의 역할과 사용 규칙

**이 문서가 정하는 것**

- 서비스 전체의 화면 계층 구조와 메뉴 구성
- 각 화면의 고유 ID, 계층 레벨, MVP 포함 여부
- 액터(관리자 / 일반 사용자)별 진입 경로
- 화면 간 부모–자식 관계
- 시나리오 카탈로그의 구조와 화면 연결 규칙. §5-6의 스키마는 시나리오가 어느 화면을 어떤 상태로
  여는지를 정하는 것이며 저장 모델이 아니다

**이 문서가 정하지 않는 것**

- 화면별 위젯 · 기능 상세 명세
- 와이어프레임 · UI 디자인
- 데이터 모델, API 스펙, 수집 파이프라인
- 파이프라인 운영 표면 — 수집 실패 데이터의 복구·재처리는 내부 운영 도구(배치 · CLI)로 수행하며
  관리자 화면을 두지 않는다. 관측성(CloudWatch · Sentry)도 마찬가지다

**운영 규칙**

1. 새 화면을 추가하거나 계층을 바꾸려면 이 문서를 먼저 수정한 뒤 구현에 들어간다.
2. 화면 ID(`노드 ID`)는 다이어그램 ↔ 문서 ↔ 코드를 잇는 매핑 키이므로 임의로 바꾸지 않는다.
3. `[향후]` 표시된 화면은 MVP 구현 대상이 아니지만, 라우팅 · 네비게이션 구조 설계 시 자리를 비워둔다.
4. 판단이 필요한 항목은 임의로 결정하지 말고 9장 미확정 목록에 추가한다.

## 2. 범례 · 표기 규칙

| 표기 | 의미 |
| --- | --- |
| `[MVP]` | 1차 출시 범위 |
| `[향후]` | Post-MVP 확장 계획 |
| `노드 ID` | 화면 식별자. 다이어그램 ↔ 문서 ↔ 코드를 잇는 매핑 키 |
| `L0`~`L5` | 계층 깊이. L0 서비스 → L1 액터 → L2 영역 → L3 메뉴 → L4 서브메뉴 → L5 상세 |

## 3. 전체 구조 한눈에

관리자 영역은 성격이 다른 두 축으로 나뉜다 — 지표를 보는 대시보드와 서비스를 커스터마이징하는 조직
설정이다. 화면을 추가할 때 어느 축인지 먼저 정한다.

```
Pulsemetry (L0)
│
├── 관리자 [MVP]  ......................................... L1
│   ├── 가입 · 로그인 [MVP]  .............................. L2
│   ├── 관리자 대시보드 — 지표 [MVP]  ..................... L2
│   │   ├── 시나리오 런처 [MVP]  .......................... L3   전역 오버레이 · 라우트 없음
│   │   ├── Overview [MVP]  ............................... L3   조직 전체 지표
│   │   ├── Activity [MVP]  ............................... L3
│   │   ├── Members [MVP]  ................................ L3   구성원 개인 지표
│   │   ├── Cost & Models [MVP]  .......................... L3   모델 · 비용 지표
│   │   ├── Teams [향후]  ................................. L3   팀 단위 비교 지표
│   │   ├── Projects [향후]  .............................. L3
│   │   ├── Insights [향후]  .............................. L3   스킬 관련 지표
│   │   ├── Alerts [향후]  ................................ L3
│   │   └── Budgets [향후]  ............................... L3   예산 관련 지표
│   └── 조직 설정 — 관리 [MVP]  ........................... L2
│       ├── Organization [MVP]  ........................... L3
│       │   ├── Organization Info [MVP]  .................. L4
│       │   ├── 조직 구성 (Teams 관리) [MVP]  ............. L4   조직-팀-사원 매핑
│       │   ├── AI Provider 계약 [MVP]  ................... L4   토큰당 단가 계약 입력
│       │   └── Members 관리 [MVP]  ....................... L4
│       │       ├── 구성원 목록 [MVP]  .................... L5
│       │       ├── 구성원 역할 [MVP]  .................... L5
│       │       └── 설치 상태 [MVP]  ...................... L5
│       ├── Policies [MVP]  ............................... L3   조직 전체 수집 설정
│       │   ├── 정책 요약 [MVP]  .......................... L4
│       │   ├── OTLP [MVP]  ............................... L4
│       │   ├── Signals [MVP]  ............................ L4
│       │   ├── Privacy [MVP]  ............................ L4
│       │   ├── 마스킹 규칙 [MVP]  ........................ L4
│       │   ├── Repository Allowlist [MVP]  ............... L4
│       │   ├── Resource Attributes [MVP]  ................ L4
│       │   └── Manifest History [향후]  .................. L4
│       ├── Settings [MVP]  ............................... L3
│       │   ├── 서비스 설정 [MVP]  ........................ L4
│       │   └── 설치 초대 발송 [MVP]  ..................... L4   초대 · 재발급 · 코드 상태
│       └── Integrations [향후]  .......................... L3
│
└── 일반 사용자 [MVP]  .................................... L1
    └── 설치 안내 이메일 [MVP]  ........................... L2
        ├── 설치 페이지 (Web) [MVP]  ...................... L3   OS 자동 감지 · 로그인 없음
        │   └── 개인 설치 명령 [MVP]  ..................... L4
        │       └── 로컬 설치 (데몬 GUI) [향후]  .......... L5
        │           ├── 활동 요약 (토큰/비용 확인) [향후]
        │           ├── 도구 연동 [향후]
        │           ├── 수집 항목 확인 (정책) [향후]
        │           └── 설정 (프로필 제외) [향후]
        └── 문제 해결 · 재발급 안내 [MVP]  ................ L3
```

`시나리오 런처(scn)`는 메뉴가 아니라 대시보드 전역에 걸리는 오버레이다. 자기 화면을 갖지 않으며,
시나리오를 고르면 L3 지표 화면으로 이동시킨다. 계층상 자리를 여기 잡아둔 것은 노드 ID를 둘 곳이
필요해서다.

`구성원 초대`는 Members 관리가 아니라 Settings에 있다. 초대 발송의 소유자는 한 곳이어야 하고, 그 자리는
Settings다. Members 관리에서는 설치 상태를 볼 뿐 발송하지 않는다.

## 4. 진입점 · 액터

서비스는 두 개의 액터로 갈라지며, 두 경로는 서로 다른 제품 표면을 쓴다. 팀장(Manager) 역할은 두지
않는다 — 팀은 조직 구성 데이터로 존재하지만 별도 권한 주체가 아니다.

| 액터 | 노드 ID | 진입점 | 제품 표면 | 범위 |
| --- | --- | --- | --- | --- |
| 관리자 | `admin` | 가입 · 로그인 | 웹 대시보드(지표) + 조직 설정 | `[MVP]` |
| 일반 사용자 | `user` | 설치 안내 이메일 | 이메일 → 설치 페이지(웹, 로그인 없음) → CLI | `[MVP]` |

MVP에서 일반 사용자는 웹에 로그인하지 않는다. 설치 페이지는 OS를 감지해 설치 명령어를 보여주는 안내
표면일 뿐이고, 사용자를 식별하는 것은 초대 코드다. 명령을 실행하면 그 뒤는 전부 CLI에서 일어난다.
개인용 화면(데몬 GUI)은 전부 `[향후]` 다.

## 5. 관리자 영역

대시보드는 지표를, 조직 설정은 관리를 담당한다. 이 구분이 이 장의 골격이다.

- **대시보드**는 조직 전체 · 팀 · 구성원 개인 단위 지표를 보여주고, 그 밖에 모델 · 예산 · 스킬 같은
  분류가 더 붙을 수 있다(예산 · 스킬 계열은 `[향후]`). 여기서는 아무것도 설정하지 않는다.
- **조직 설정**은 관리자가 서비스를 쓰기 위해 커스터마이징하는 곳이다 — 조직-팀-사원 매핑, 조직이
  AI Provider와 맺은 계약 입력, 조직 전체에 통용되는 수집 · 마스킹 정책이 여기 들어간다.

### 5-1. 관리자 대시보드(지표) — L3 메뉴

| # | 메뉴 | 노드 ID | 범위 | 목적 |
| --- | --- | --- | --- | --- |
| 0 | 시나리오 런처 | `scn` | `[MVP]` | 질문 기준으로 볼 지표를 고르는 전역 표면. 메뉴가 아니다 |
| 1 | Overview | `ov` | `[MVP]` | 조직 전체 AI 운영 상태 요약 |
| 2 | Activity | `act` | `[MVP]` | 사용 활동 내역 조회 |
| 3 | Members | `dv` | `[MVP]` | 구성원별 사용량 · 비용 (지표 전용) |
| 4 | Cost & Models | `cm` | `[MVP]` | 비용 발생 지점 · 모델별 분석. 공시 기준 금액(적재 시 저장)과 계약 적용 금액(조회 시 계산)을 구분해 표시 |
| 5 | Teams | `tm` | `[향후]` | 팀 단위 사용량 · 비용 비교 |
| 6 | Projects | `pj` | `[향후]` | 프로젝트 단위 조회 |
| 7 | Insights | `ins` | `[향후]` | 효율 어드바이스 · 스킬 관련 지표 |
| 8 | Alerts | `al` | `[향후]` | 이상 징후 알림 |
| 9 | Budgets | `bg` | `[향후]` | 예산 지표 · 초과 관리 |

### 5-1-1. 조직 설정(관리) — L3 메뉴

| # | 메뉴 | 노드 ID | 범위 | 목적 |
| --- | --- | --- | --- | --- |
| 1 | Organization | `org` | `[MVP]` | 조직 정보 · 조직 구성 · 계약 · 구성원 운영 |
| 2 | Policies | `pol` | `[MVP]` | 조직 전체 데이터 수집 · 마스킹 설정 |
| 3 | Settings | `set` | `[MVP]` | 서비스 설정 · 설치 초대 발송 |
| 4 | Integrations | `ig` | `[향후]` | 외부 도구 연동 |

`Members(dv)`와 `Organization > Members 관리(om)`는 분리 유지한다. 전자는 사용량 · 비용을 보는 지표
화면, 후자는 계정 · 역할 · 설치 상태를 다루는 운영 화면이며 읽는 데이터도 다르다(전자는 Signal 집계,
후자는 구성원 · 설치 등록).

`Teams(tm)`가 `[향후]`인 것은 팀 단위 비교 화면에 한정된다. 조직-팀-사원 데이터 모델과 `조직
구성(Teams 관리)` 화면은 `[MVP]`이며, 대시보드의 팀 필터도 MVP다.

### 5-2. Organization (L4 ~ L5)

| 화면 | 노드 ID | 계층 | 범위 | 내용 |
| --- | --- | --- | --- | --- |
| Organization Info | `oi` | L4 | `[MVP]` | 조직 기본 정보 |
| 조직 구성 (Teams 관리) | `ot` | L4 | `[MVP]` | 조직-팀-사원 매핑. 팀 생성 · 편집 · 구성원 배치 |
| AI Provider 계약 | `oc` | L4 | `[MVP]` | 조직이 각 Provider와 맺은 토큰당 단가 계약 입력 · 수정 |
| Members 관리 | `om` | L4 | `[MVP]` | 구성원 운영 (아래 3개 하위 화면) |
| ├ 구성원 목록 | `m1` | L5 | `[MVP]` | 전체 구성원 조회 |
| ├ 구성원 역할 | `m2` | L5 | `[MVP]` | 역할 부여 · 변경 (관리자 / 일반 사용자 2역할) |
| └ 설치 상태 | `m3` | L5 | `[MVP]` | 구성원별 CLI 설치 · 수집 연결 상태 |

두 액터가 만나는 지점은 `Settings > 설치 초대 발송(s2)` 이다. 여기서 발송한 초대가 일반 사용자 경로의
`설치 안내 이메일(mail)` 을 촉발하므로 구현 시 함께 설계한다. `Members 관리(om)` 는 그 결과인 설치
상태를 볼 뿐 발송하지 않는다.

`AI Provider 계약(oc)` 에 입력된 조직 계약 단가를 `Cost & Models(cm)` 지표가 조회 시점에 적용해 조직이
실제로 부담하는 금액을 산출한다.

단, 그것이 화면에 나오는 유일한 금액은 아니다. Provider 공시 단가 기준의 금액은 수집 시점에 이미
계산돼 저장돼 있다. 계약을 아직 입력하지 않은 조직에는 이 값이 그대로 보이며, 계약을 입력한 뒤에는
기준선 비교에 쓴다. 두 값은 이름을 구분해 표시하고 섞지 않는다.

### 5-3. Policies (L4)

Policies는 AI 사용을 통제하는 정책이 아니라, 조직 전체에 통용되는 데이터 수집 설정이다. 관리자가
마스킹 범위를 커스터마이징하는 기능도 여기에 속한다.

| 화면 | 노드 ID | 범위 | 내용 |
| --- | --- | --- | --- |
| 정책 요약 | `p1` | `[MVP]` | 현재 적용 중인 수집 정책 한눈에 보기 |
| OTLP | `p2` | `[MVP]` | OTLP 수집 엔드포인트 설정 |
| Signals | `p3` | `[MVP]` | 수집할 시그널 종류 선택 |
| Privacy | `p4` | `[MVP]` | 민감정보 수집 여부 (프롬프트 · 응답 · tool 내용 등) |
| 마스킹 규칙 | `p8` | `[MVP]` | 관리자가 마스킹 대상 · 방식을 커스터마이징 |
| Repository Allowlist | `p5` | `[MVP]` | 수집 대상 저장소 허용 목록 |
| Resource Attributes | `p6` | `[MVP]` | 리소스 속성 정의 |
| Manifest History | `p7` | `[향후]` | 정책 변경 이력 추적 |

`Privacy(p4)` 는 "무엇을 수집할 것인가", `마스킹 규칙(p8)` 은 "수집한 것에서 무엇을 가릴 것인가"로
나뉜다. 두 화면이 별개인 이유다.

두 화면은 실제 파이프라인 동작으로 이어진다. `Privacy(p4)` 에서 프롬프트 수집을 켜면 프롬프트가
서버로 전송되고, `마스킹 규칙(p8)` 에서 관리자가 지정한 민감정보를 서버 Masker가 가린다. 수집을
꺼두면 데몬이 전송 전에 제거하므로 서버에 도달하지 않는다.

### 5-4. Settings (L4)

| 화면 | 노드 ID | 범위 | 내용 |
| --- | --- | --- | --- |
| 서비스 설정 | `s1` | `[MVP]` | 서비스 · 앱 수준 설정 |
| 설치 초대 발송 | `s2` | `[MVP]` | 초대 발송 단일 소유자. 초대 코드 상태 조회 · 재발급 |

### 5-5. Overview 구성 후보

Overview에 담을 후보로 남아 있는 항목이다. 아직 확정된 명세가 아니다.

1. KPI
2. 작업 분포 — 코드 생산에 썼는지, 테스트에 썼는지
3. 팀별 요약, 이상 탐지, 알림
4. 비용 관련 — 모델별 / 팀별 비용

2번은 `[향후] Insights`, 3번의 이상 탐지 · 알림은 `[향후] Alerts` 와 범위가 겹친다. MVP Overview에
어디까지 담을지 결정이 필요하다(9장 미확정 #2).

팀별 요약과 팀별 비용은 MVP에 남는다 — 조직 구성이 MVP이므로 팀 필터가 성립한다. `[향후] Teams` 는
팀 단위 비교 전용 화면을 가리킨다.

### 5-6. 시나리오 엔진

관리자는 알고 싶은 것이 있어도 그 답이 어느 화면의 어떤 지표에서 나오는지 모른다. 지표를 나열하는
대신 답하고 싶은 질문을 먼저 고르게 하고, 그 질문에 맞는 화면과 지표 구성을 자동으로 적용한다.

**카테고리 8종**

| 카테고리 | 다루는 질문 | 비고 |
| --- | --- | --- |
| 비용·예산 | 어디에 얼마를 쓰고 있는가, 예산은 언제 소진되는가 | |
| 사용 패턴·리밋 | 어떻게 쓰고 있는가, 리밋에 막히고 있는가 | |
| 도입·채택 | 발급한 좌석이 실제로 쓰이고 있는가 | |
| 생산성·역량 | 제안을 받아들이는가, 어디서 막히는가 | |
| 보안·컴플라이언스 | 토큰과 접근이 정책대로 관리되고 있는가 | |
| 품질·운영 | 실패와 수집 중단이 방치되고 있는가 | |
| 거버넌스 | 조직 자산이 어디에 쓰이고 무엇이 미지정인가 | |
| ROI·경영보고 | 경영 보고에 쓸 수치를 뽑을 수 있는가 | 절감 시간과 매출 기여는 텔레메트리로 계산되지 않는다 |

**시나리오 레코드 스키마**

| 필드 | 내용 |
| --- | --- |
| `id` | 시나리오 식별자. `{카테고리}-{슬러그}` 형식 |
| `category` | 위 8종 중 하나 |
| `question` | 관리자가 답을 얻고 싶은 질문 한 문장 |
| `metrics[]` | 답에 필요한 지표. 지표 레지스트리에 정의된 ID만 쓴다 |
| `target.screen` | 적용할 대시보드 화면 노드 ID |
| `target.filters` | 미리 적용할 기간 · 팀 · 분해 축 |
| `target.focus[]` | 강조할 위젯 |
| `action` | 답을 얻은 뒤 관리자가 취할 조치 |
| `caveat` | 측정 한계. 값이 있으면 적용 컨텍스트 바에 항상 노출한다 |
| `requires[]` | 가용성 판정 입력. 필요한 수집 정책 · 관리자 입력 항목 |
| `status` | 제품 구현 상태. `제공` 또는 `준비 중` |

지표 레지스트리는 시나리오가 참조할 수 있는 지표 ID의 정의 목록이다. 각 지표가 어떤 수집 정책과
관리자 입력에 의존하는지 선언하며, 이 선언이 가용성 판정의 입력이 된다.

**가용성 3단계**

| 가용성 | 의미 | 판정 근거 | 화면 동작 |
| --- | --- | --- | --- |
| 지금 확인 가능 | 조직의 현재 수집 데이터로 답이 나온다 | `requires`가 모두 충족 | 바로 적용 |
| 설정 필요 | 관리자 조치가 선행돼야 한다 | 미충족 `requires` 항목이 있음 | 선행 조건과 해당 설정 화면 링크를 함께 표시 |
| 곧 지원 | 데이터는 오지만 화면이 아직 없다 | `status`가 `준비 중` | 적용 불가. 목록에는 남긴다 |

앞의 두 값은 조직마다 다르다. 같은 시나리오가 A 조직에는 `지금 확인 가능`, B 조직에는 `설정 필요`로
보인다. `곧 지원`만 조직과 무관한 제품 상태다.

**카테고리별 대표 예시**

| 카테고리 | 질문 | 연결 화면 | 가용성 |
| --- | --- | --- | --- |
| 비용·예산 | 어떤 부서가 예산을 조기 소진하고 있는가 | `cm` | 지금 확인 가능 |
| 사용 패턴·리밋 | 리밋으로 요청이 최종 실패한 팀이 있는가 | `ov` | 지금 확인 가능 |
| 도입·채택 | 몇 달째 안 쓰는 좌석이 있는가 | `dv` | 지금 확인 가능 |
| 생산성·역량 | AI 제안을 어느 언어에서 가장 많이 거절하는가 | `act` | 지금 확인 가능 |
| 보안·컴플라이언스 | 한 토큰이 여러 머신에서 동시에 쓰이고 있는가 | `dv` | 지금 확인 가능 |
| 품질·운영 | 수집이 끊긴 좌석이 며칠째 방치되고 있는가 | `ov` | 지금 확인 가능 |
| 거버넌스 | 어떤 MCP 서버와 서브에이전트가 비용을 쓰는가 | `cm` | 설정 필요 |
| ROI·경영보고 | 월별 부서 비용을 경영 보고 형식으로 내보낼 수 있는가 | `cm` | 곧 지원 |

카테고리마다 하나씩만 옮긴 것이다. 카탈로그 전체 목록은 코드가 소유하며 이 문서에 옮겨 적지 않는다.

**런처 동작**

1. 대시보드 어느 화면에서든 전역 헤더에서 연다.
2. 카테고리로 좁히거나 검색한다. 검색 대상은 질문 · 지표명 · 액션 · 카테고리명이다.
3. 시나리오를 고르면 대상 화면으로 이동하고 기간 · 팀 · 분해 축이 미리 적용되며 관련 위젯이 강조된다.
4. 화면 상단 적용 컨텍스트 바에 질문 · 필요 지표 · 단서 · 선행 조건이 남는다. 해제할 수 있다.

MVP 런처의 입력창은 카탈로그를 검색할 뿐 자유 질의를 받지 않는다.

**화면 연결 제약**

MVP 카탈로그의 `target.screen`은 MVP 화면(`ov` · `act` · `dv` · `cm`)만 쓴다. `[향후] Teams(tm)` 를
향하는 팀 비교 시나리오는 `곧 지원`으로 둔다. 팀 필터는 MVP이므로 팀 관점 질문 상당수는 `ov` · `cm`
에 팀 분해 축을 적용해 성립한다.

**인접 화면과의 경계**

시나리오 엔진은 지표를 해석하거나 조언하지 않는다. 어떤 지표를 볼지 고르는 내비게이션 보조이며 새
지표를 만들지 않는다. `[향후] Insights` (스킬 지표)와 `[향후] Alerts` (이상 징후)는 지표 자체를
추가하는 화면이므로 성격이 다르다.

## 6. 일반 사용자 영역 (온보딩 경로)

### 6-1. MVP 경로

```
설치 안내 이메일 (mail)
   ├── 설치 페이지 Web (web)          → OS 자동 감지 · 명령어 표시 (로그인 없음)
   │      └── 개인 설치 명령 (cmd)    → 복사해서 실행하면 수집 시작
   └── 문제 해결 · 재발급 안내 (help) → 설치 실패 · 링크 만료 대응
```

| 화면 | 노드 ID | 계층 | 범위 | 내용 |
| --- | --- | --- | --- | --- |
| 설치 안내 이메일 | `mail` | L2 | `[MVP]` | 관리자 초대로 발송되는 진입점 |
| 설치 페이지 (Web) | `web` | L3 | `[MVP]` | OS 자동 감지 · 설치 안내. 로그인 없음 |
| 개인 설치 명령 | `cmd` | L4 | `[MVP]` | 사용자별 고유 설치 명령(초대 코드 포함) 제공 · 복사 |
| 문제 해결 · 재발급 안내 | `help` | L3 | `[MVP]` | 설치 실패 · 재발급 가이드 |

명령을 실행하면 부트스트랩 스크립트가 바이너리를 내려받고, CLI가 초대 코드로 등록한 뒤 도구 설정
주입 · 로컬 배선 · 데몬 자동 실행 등록까지 이어서 수행한다. 이 뒤로는 화면이 없다.

### 6-2. 로컬 설치 데몬 GUI (전체 `[향후]`)

| 화면 | 노드 ID | 계층 | 내용 |
| --- | --- | --- | --- |
| 로컬 설치 (데몬 GUI) | `loc` | L5 | 개인 로컬 클라이언트 화면 |
| ├ 활동 요약 | `l1` | L6 | 본인 토큰 · 비용 확인 |
| ├ 도구 연동 | `l2` | L6 | 로컬 도구 연결 |
| ├ 수집 항목 확인 | `l3` | L6 | 어떤 데이터가 수집되는지 투명성 확인 |
| └ 설정 (프로필 제외) | `l4` | L6 | 로컬 설정. 프로필 기능은 범위 밖 |

이 화면들이 읽을 로컬 데이터 계층(클라이언트 SQLite)과 조회 인터페이스는 이미 존재한다. `[향후]`로
남은 것은 화면 자체뿐이다.

## 8. Post-MVP 목록

MVP에서 의도적으로 제외한 항목이다. 삭제가 아니라 연기이므로 구조상 자리를 유지한다.

| 화면 | 노드 ID | 위치 | 연기 사유 |
| --- | --- | --- | --- |
| Teams (팀 비교 지표) | `tm` | 대시보드 L3 | 팀 단위 비교는 오판 위험. 먼저 raw 정확도 확보. 조직 구성 관리(`ot`)와 팀 필터는 MVP |
| Integrations | `ig` | 조직 설정 L3 | MVP 데이터 원천은 Claude Code · Codex 두 CLI 한정. 그 밖의 도구(Gemini CLI · Cursor 등) 연동은 연기. Enricher의 외부 연동(GitHub 등)도 확장 지점만 정의하고 MVP에서 구현하지 않는다 |
| Projects | `pj` | 대시보드 L3 | 프로젝트 단위 집계는 가시화 이후 |
| Insights (스킬 지표) | `ins` | 대시보드 L3 | '잘 쓴다'의 정의가 가장 어려운 챌린지 |
| Alerts | `al` | 대시보드 L3 | 임계값 기준 미정 |
| Budgets (예산 지표) | `bg` | 대시보드 L3 | 예산 통제는 가시화 이후 단계 |
| Manifest History | `p7` | Policies L4 | 정책 변경 이력은 정책 운영이 자리 잡은 뒤 |
| 자유 질의 시나리오 (LLM) | `scn` | 대시보드 L3 | 사전 정의 카탈로그로 먼저 검증. 생성 결과의 지표 범위 제한과 검증 절차가 선행 |
| 로컬 데몬 GUI 일체 | `loc`, `l1`~`l4` | 사용자 L5~L6 | MVP는 CLI 설치만으로 수집 성립. 데이터 계층은 이미 있고 화면만 연기 |
