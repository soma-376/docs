## 0. 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | Pulsemetry |
| 작성자 / 팀 | 3대 76 |
| 한 줄 요약 | Claude Code · Codex 등 개발 AI 도구의 사용량과 비용을 한곳에 모으고, 조직 → 팀 → 구성원 축으로 나눠 보며, 조직이 맺은 계약 단가로 실비용을 환산하고, 관리자가 답을 얻고 싶은 질문을 고르면 그 답이 있는 화면을 여는 AI 개발도구 사용 통합·가시화 플랫폼 |

**제품 원칙**

1. AI 사용을 막는 게 아니라, 안전하고 효율적으로 쓰도록 돕는다.
2. 프롬프트 수집 여부는 조직의 Privacy 정책이 정하고, 수집한 것은 마스킹 이후에만 저장한다. 마스킹은 클라이언트 데몬과 서버 두 곳에서 집행한다.
3. 금액은 두 값으로 나뉜다 — 공시 단가 기준 금액과 조직 계약 단가 적용 금액. 두 값은 이름을 구분해 표시하고 섞지 않는다.
4. raw 정확 수집 → 표시 → 그다음 인사이트.

**제품 형태**

> 웹 대시보드(Admin Console), 설치 온보딩(이메일 · 웹 · CLI), 데스크탑 데몬 세 개의 사용자 접점으로 이루어진 사내 AI 사용 통합·가시화 플랫폼. 그 위에 ① 조직 · 팀 · 구성원 축 집계와 계약 단가 기반 실비용 ② 질문 기반 시나리오 런처 ③ 조직이 정하는 수집 · 마스킹 정책이 얹힌다.

데몬은 인라인 프록시이자 프라이버시 1차 집행 지점이다. 데몬이 죽으면 배선된 상태에서 텔레메트리가 유실되므로 설치 시 로그인 자동 실행을 함께 등록한다. 제품 표면이 웹 하나가 아니라는 사실은 온보딩, 지원, 보안 심사 전부에 영향을 준다.

## 1. 데스크 리서치

### 1-1. 시장 / 트렌드 분석

거버넌스 레이어는 통상 관리 대상 지출의 3~7%를 가져간다(클라우드 FinOps 툴의 역사적 비율 기준).

| 구분 | 산정 근거 | 규모 |
| --- | --- | --- |
| TAM | 글로벌 AI 코딩 도구 시장 2026년 약 93.5억 달러 × 5% | 연 4~6억 달러 (2030년 15~30억 달러) |
| SAM | 국내 100인 이상 개발조직 유료 시트 약 7~10만 석 × $4/석/월 | 연 50~150억 원 |
| SOM | 3년차, SAM의 5~10% 침투 | 연 5~15억 원 / 고객사 30~60곳 |

> **교차 검증(Bottom-up):** 전 세계 전문 개발자 약 3,000만 명 중 기업 관리 하에 유료 AI 도구를 쓰는 인원을 1,000만 명으로 가정, 좌석당 월 $3~5 → 연 3.6~6억 달러. Top-down 추정과 일치.

> ⚠️ **아직 선택하지 않은 갈림길**
> 국내만 보면 SAM이 연 150억 원 이하다. 아래 셋 중 하나를 명시적으로 선택해야 한다.
> 1. 처음부터 글로벌 SaaS로 설계 (영문 우선, 셀프서브 온보딩)
> 2. 개발도구를 넘어 전사 AI 지출로 범위 확장 (비개발 부서 포함)
> 3. 사내 도구 또는 부트스트랩 규모로 정직하게 설계

*2026년 시장 규모는 조사기관별로 93.5억~161.3억 달러까지 벌어진다. 위 TAM은 보수적 구간을 채택한 추정치다.*

**시장 신호**

- Gartner는 2026년 전 세계 AI 지출을 2.59조 달러(전년 대비 +47%)로 전망.
- Uber는 약 5,000명 엔지니어의 사용량 급증으로 2026년 AI 코딩 예산 전액을 4월에 소진한 것으로 보도됨.
- Microsoft는 회계연도 마감(6/30) 전 한 사업부의 내부 Claude Code 라이선스를 취소.
- IBM 조사에서 CIO·CTO의 약 2/3가 "완전히 통제하지 못하는 AI 시스템에 대해 책임을 지고 있다"고 응답.

**기술 트렌드**

- 과금 모델이 좌석당 정액 SaaS에서 사용량 비례 변동비로 바뀌었다. 예산이 예측 가능하게 움직이지 않는다.
- 도구가 분화되고(Claude Code · Codex · Cursor · Copilot) 결제 주체가 혼재한다(개인 구독 / 법인카드 / API).
- 에이전트 루프가 하루 만에 예산을 태울 수 있으나 월말 청구서 전까지 감지되지 않는다.
- 외부 SaaS로의 사내 프롬프트 유출이 보안 심사의 1차 관문이다. 무엇을 수집하고 무엇을 가리는지가 계약 조건이 된다.

**핵심 시사점**

1. 통합은 여전히 필요하지만, 벤더가 하는 통합과 우리가 하는 통합은 범위가 다르다. 벤더 콘솔은 자기 벤더의 지출만 본다. 팀이 워크로드를 Claude Code에서 Codex로 옮긴 사실은 어느 벤더도 알 수 없다.
2. 다만 모아서 보여주기만으로는 지불 근거가 약하다. 통합은 전제이고, 그 위에 무엇을 얹느냐가 제품이다.
3. 사용자 → 팀 매핑과 조직이 벤더와 맺은 계약 단가는 사내 정보이므로 벤더가 원리적으로 알 수 없다. 구조적으로 방어 가능한 축이다.
4. 관리자는 물어볼 줄 아는 것만 물을 수 있다. 지표를 나열하는 화면은 안 보게 된다. 질문에서 출발해 화면으로 데려다주는 것이 대시보드가 살아남는 조건이다.

### 1-3. 차별화 가설

> 우리는 벤더 콘솔·범용 옵저버빌리티와 달리, 개발 AI 도구를 도구 횡단으로 통합한 대시보드 위에 ① 조직 → 팀 → 구성원 축 집계와 조직이 맺은 계약 단가 기반 실비용 환산, ② 관리자가 질문을 고르면 그 답이 있는 화면과 필터가 적용되는 시나리오 런처, ③ 조직이 직접 정하는 수집 범위와 마스킹 규칙(클라이언트·서버 이중 집행)을 제공하여, AI 지출을 조직·팀 단위로 설명하고 책임져야 하는 개발 조직 리더에게 가치를 준다.

| 층 | 내용 | 방어력 |
| --- | --- | --- |
| 기반 | 도구 횡단 통합 수집·가시화 (Claude Code · Codex) | 벤더는 못 함(자기 벤더만). 서드파티와는 동률 |
| 차별 | 조직·팀 축 집계 + 계약 단가 실비용 + 시나리오 런처 | 벤더는 사내 조직도도 계약 단가도 모른다. 서드파티 대비 가볍고 저렴 |
| 해자 | 조직별 수집·마스킹 정책 커스터마이징과 이중 집행 | 보안 심사 통과 자체가 진입장벽. 다만 아래 경고 참조 |

> ⚠️ **해자 층의 근거가 약하다.** "조직이 마스킹 규칙을 직접 정하고 클라이언트·서버 두 곳에서 집행한다"는 경쟁사도 구현할 수 있는 기능이다. 해자를 무엇으로 세울지는 열린 질문이며, 현재 후보는 ① 조직별 룰 축적 ② 국내 폐쇄망·계약 요건 대응 ③ 도구 횡단 커버리지 셋이다. §5-1 가설 3의 검증 결과로 판단한다.

## 2. 🧭 Empathize

> 본 섹션은 멘토 4인의 전문가 인터뷰, 팀 내부 데이터 탐색, 아이디어 검증 데스크 리서치, 설계 확정 과정에서 드러난 사실에 기반한다. 실사용자 인터뷰는 미진행이며 §5의 검증으로 보강한다.

### 2-1. 리서치 계획

| 항목 | 내용 |
| --- | --- |
| 리서치 목적 | ① 관리자가 무엇을 모르고 있는지 ② 알려주면 실제로 행동하는지 ③ 수집 범위와 마스킹 규칙을 어디까지 열어야 도입 심사를 통과하는지 |
| 대상자 정의 | ① 전문가 멘토 4인 (강성욱, 허소영, 정원용, 최승표)<br>② 개발자 100~1,000명 규모 조직의 CTO / VP Eng / 플랫폼 리드 5개사 *(모집 예정)*<br>③ 정보보안 담당자 |
| 방법론 | ☑ 1:1 인터뷰 ☑ 데스크 리서치 ☑ 대시보드 시안 컨셉 테스트 ☑ Wizard of Oz ☐ FGI ☐ 설문 |
| 진행 기간 | 2026-06-16 ~ 진행 중 (Wizard of Oz는 2주 스프린트) |
| 주요 질문 | 1. 팀별 AI 활용 현황을 따로 관리하고 있나?<br>2. AI 비용을 어느 조직 단위로 귀속시키나? 그 집계는 누가 어떻게 하나?<br>3. 지금 쓰는 도구는 몇 종인가? Claude Code·Codex 외에 무엇이 있나?<br>4. Provider와 맺은 계약 단가를 알고 있나? 그 단가로 환산된 팀별 금액을 보면 무엇이 달라지나?<br>5. 이 리포트를 받고 실제로 무엇을 했나? (2주 후 재접촉)<br>6. 프롬프트가 외부로 나가는 것 자체가 문제인가, 저장되는 것이 문제인가?<br>7. 어디까지 마스킹하면 심사에 올릴 수 있나? 마스킹 규칙을 조직이 직접 정할 수 있으면 판단이 달라지나?<br>8. 마스킹 완료본을 재처리 목적으로 보관하는 것은 수용 가능한가? 보존 기간은 얼마여야 하나?<br>9. 개발자가 각자 초대 링크로 설치하는 방식으로 전사 커버리지를 확보할 수 있나? 미설치자는 누가 독촉하나? |

### 2-2. 리서치 결과 정리 (Unpack)

| 발언 / 관찰 사실 | 출처 | 1차 해석 |
| --- | --- | --- |
| "토큰은 '원료'와 같다. 전기·밀가루처럼 아껴 쓸 니즈가 생긴다" | 허소영 6/16 | 변동비로 인식되는 순간 관리 니즈가 자연 발생 |
| "매니지먼트되는 것 자체가 가치" | 강성욱 6/29 | 절감 이전에 통제 가능 상태가 구매 이유 |
| "회사는 이런 대시보드에 자체 리소스를 쓰기 싫어 돈 주고 산다" | 강성욱 | 인건비·유지보수 회피 = 명확한 구매 동기 |
| "사준 만큼 잘 쓰는지가 진짜 문제" | 강성욱, 허소영 | 비용 자체가 아니라 ROI 관점의 불안 |
| "'이해' 자체는 제품이 아니다 — 관리자의 결정을 더 빠르고 쉽게 만들 때 가치" | 허소영 | 결정 지원이 최종 가치 지점 |

| 구성요소 | 내용 |
| --- | --- |
| User | 개발 조직의 AI 지출을 조직·팀 단위로 설명하고 책임져야 하는 CTO / VP Eng / 플랫폼 리드 |
| Situation | 도구가 여러 종으로 흩어져 있고, 각 벤더 콘솔은 자기 지출만 사용자 단위로, 그것도 공시 단가 기준으로 보여주는 상황 |
| Problem | 한 화면에 모으는 것부터 수작업이고, 모아도 팀 단위로 떨어지지 않으며 우리가 실제 내는 금액도 아니고, 지표가 많아도 어느 화면을 열어야 하는지 몰라 결국 안 보게 된다 |
| Insight | 그들이 원하는 것은 더 많은 지표가 아니라, 자기가 던지고 싶은 질문에서 출발해 곧바로 답이 있는 화면에 도착하는 경험이기 때문이다 |

**최종 POV 문장**

> 개발 조직의 AI 지출을 책임지는 CTO·플랫폼 리드는, 여러 도구에 흩어진 비용을 한 화면에 모으는 것조차 수작업이고, 모아도 팀 단위로 떨어지지 않으며 우리 계약 단가가 반영되지도 않고, 무엇을 봐야 할지조차 모르는 문제를 겪는다. 왜냐하면 그들이 진짜로 원하는 것은 더 많은 지표가 아니라, "우리 계약 기준으로 어느 팀이 얼마를 쓰는가"라는 자기 질문에서 출발해 그 답이 있는 화면으로 곧장 도착하는 경험이기 때문이다.

제품이 주는 것은 절감 권고가 아니라 질문에서 화면으로의 도달이다. 절감 권고는 효율 어드바이스 영역으로 남긴다.

### 4-3. 시나리오 엔진

관리자는 알고 싶은 것이 있어도 그 답이 어느 화면의 어떤 지표에서 나오는지 모른다. 지표를 나열하는 대신 답하고 싶은 질문을 먼저 고르게 하고, 그 질문에 맞는 화면과 지표 구성을 자동으로 적용한다.

시나리오는 네비게이션 보조다. 지표를 해석하거나 조언하지 않고 새 지표를 만들지도 않는다. 이 선을 지키면 아직 정의되지 않은 "좋은 조언"을 제품이 떠맡지 않아도 된다.

**카테고리 8종**

| 카테고리 | 다루는 질문 | 대표 예시 | 연결 화면 |
| --- | --- | --- | --- |
| 비용·예산 | 어디에 얼마를 쓰고 있는가, 예산은 언제 소진되는가 | 어떤 부서가 예산을 조기 소진하고 있는가 | Cost & Models |
| 사용 패턴·리밋 | 어떻게 쓰고 있는가, 리밋에 막히고 있는가 | 리밋으로 요청이 최종 실패한 팀이 있는가 | Overview |
| 도입·채택 | 발급한 좌석이 실제로 쓰이고 있는가 | 몇 달째 안 쓰는 좌석이 있는가 | Members |
| 생산성·역량 | 제안을 받아들이는가, 어디서 막히는가 | AI 제안을 어느 언어에서 가장 많이 거절하는가 | Activity |
| 보안·컴플라이언스 | 토큰과 접근이 정책대로 관리되고 있는가 | 한 토큰이 여러 머신에서 동시에 쓰이고 있는가 | Members |
| 품질·운영 | 실패와 수집 중단이 방치되고 있는가 | 수집이 끊긴 좌석이 며칠째 방치되고 있는가 | Overview |
| 거버넌스 | 조직 자산이 어디에 쓰이고 무엇이 미지정인가 | 어떤 MCP 서버와 서브에이전트가 비용을 쓰는가 | Cost & Models |
| ROI·경영보고 | 경영 보고에 쓸 수치를 뽑을 수 있는가 | 월별 부서 비용을 경영 보고 형식으로 내보낼 수 있는가 | Cost & Models |

ROI·경영보고 카테고리에는 단서가 붙는다 — 절감 시간과 매출 기여는 텔레메트리로 계산되지 않는다.

**시나리오 레코드 스키마**

| 필드 | 내용 |
| --- | --- |
| `id` | 시나리오 식별자. `{카테고리}-{슬러그}` 형식 |
| `category` | 위 8종 중 하나 |
| `question` | 관리자가 답을 얻고 싶은 질문 한 문장 |
| `metrics[]` | 답에 필요한 지표. 지표 레지스트리에 정의된 ID만 쓴다 |
| `target.screen` | 적용할 대시보드 화면 |
| `target.filters` | 미리 적용할 기간 · 팀 · 분해 축 |
| `target.focus[]` | 강조할 위젯 |
| `action` | 답을 얻은 뒤 관리자가 취할 조치 |
| `caveat` | 측정 한계. 값이 있으면 적용 컨텍스트 바에 항상 노출한다 |
| `requires[]` | 가용성 판정 입력. 필요한 수집 정책 · 관리자 입력 항목 |
| `status` | 제품 구현 상태. `제공` 또는 `준비 중` |

절감액 필드는 두지 않는다. 절감액을 계산하려면 조치 전후를 비교하고 대안 모델의 비용을 추정하는 판단이 필요한데, 그것이 곧 어드바이스 엔진이다. 대신 `action`(무엇을 할 수 있는가)과 `caveat`(이 숫자를 얼마나 믿을 수 있는가)을 필수로 둔다.

**가용성 3단계**

| 가용성 | 의미 | 판정 근거 | 화면 동작 |
| --- | --- | --- | --- |
| 지금 확인 가능 | 조직의 현재 수집 데이터로 답이 나온다 | `requires`가 모두 충족 | 바로 적용 |
| 설정 필요 | 관리자 조치가 선행돼야 한다 | 미충족 `requires` 항목이 있음 | 선행 조건과 해당 설정 화면 링크를 함께 표시 |
| 곧 지원 | 데이터는 오지만 화면이 아직 없다 | `status`가 `준비 중` | 적용 불가. 목록에는 남긴다 |

앞의 두 값은 조직마다 다르다. 같은 시나리오가 A 조직에는 `지금 확인 가능`, B 조직에는 `설정 필요`로 보인다. `곧 지원`만 조직과 무관한 제품 상태다. 가용성은 저장하지 않고 조회 시 판정한다 — 저장하면 정책을 바꿀 때마다 재계산이 필요하고, 그 사이 답할 수 없는 시나리오가 답할 수 있는 것처럼 보인다.

**약속할 때 지켜야 할 선**

- 대상 화면은 이미 있는 지표 화면(Overview · Activity · Members · Cost & Models)만 쓴다. 팀 비교 화면을 향하는 시나리오는 `곧 지원`에 둔다
- 런처의 입력창은 카탈로그를 검색할 뿐 자유 질의를 받지 않는다
- 시나리오는 새 지표를 만들지 않는다. 참조하는 지표는 지표 레지스트리에 정의돼 이미 수집되고 있는 것뿐이다
- 카탈로그 전체 목록은 코드가 소유하며 기획서에 옮겨 적지 않는다. 개수와 카테고리별 배분은 미정

> ③ 마스킹을 마치기 전의 데이터는 어떤 서버 저장소에도 쓰지 않는다

> ⑤ 파이프라인 4단계는 예외 없이 작업 전후를 로깅한다. 로깅이 없으면 복구가 성립하지 않는다
> ⑥ 온보딩 필수 산출물은 초대 발송과 설치 상태(커버리지) 확인 표면이다
> ⑦ 재처리는 내부 운영 도구로만 트리거한다. 관리자 화면·API를 두지 않는다

### 5-1. 검증해야 할 핵심 가설

**가설 1 — 인사이트 가설 (최우선)**

- **실패 신호:** "흥미롭네요" 이후 아무 일도 없음
- **소요:** 2주. 부산물로 시나리오 카탈로그 초기 목록과 첫 고객 5곳
- **단서:** Wizard of Oz 리포트는 사람이 분석해 쓴 어드바이스다. 제품이 주는 것은 질문에서 화면으로의 도달이다. 이 검증이 성공해도 제품 사양이 어드바이스 엔진이 되지는 않는다 — 산출물은 관리자가 실제로 던지는 질문의 목록이며, 그것이 시나리오 카탈로그가 된다

**가설 2 — 수집 가능성 가설**

> Claude Code와 Codex 두 도구의 데이터를 실제로 같은 스키마에 담을 수 있다.

- **검증 방법:** 자체 팀 2주 수집 / Codex 시그널을 실제로 매핑해 보고 Claude Code와의 필드 대응표 작성 / 도구별 가용 범위 정리
- **성공 기준:** Codex 시그널이 `Unmapped`에서 벗어나 집계에 들어갈 것 + 두 도구의 공통 스키마와 provider별 확장 스키마 초안 확정
- **우선순위가 높은 이유:** Codex 시그널 매핑이 미구현이라 현재 집계에 들어가지 않는다. 도구가 하나면 벤더 콘솔과 구분되지 않으므로 이것은 기술 과제가 아니라 포지셔닝의 전제다
- **실패 시:** 통합 범위를 축소해 명시하고, 도구 횡단을 차별점에서 내린다

**가설 3 — 수집·마스킹 정책 가설**

> 조직이 수집 범위와 마스킹 규칙을 직접 정하고, 마스킹 이후에만 저장하는 구조로 보안 심사를 통과할 수 있다.

- **검증 방법:** 정보보안 담당 3인에게 부록 A의 처리 흐름도를 제시하고 무엇을 더 증명해야 믿는지 청취 / 기본 마스킹 룰셋을 실제 프롬프트 샘플에 적용해 정탐·오탐률 측정 / 마스킹 완료본을 재처리 목적으로 보관하는 것에 대한 수용 여부와 허용 보존 기간 청취
- **성공 기준:** ① 3인 중 2인이 "이 형태면 심사에 올릴 수 있다" ② 정형 식별자 마스킹 정탐률 90% 이상 ③ 허용 가능한 보존 기간의 하한선 확보
- **알려진 약점:** 감사 로그가 아직 범위 밖이다. 관측성 로그는 시스템이 무엇을 처리했는지의 운영 로그이지 누가 무엇을 조회·변경했는지의 감사 로그가 아니다. 보안 심사에서 이 질문은 거의 확실히 나온다
- **실패 시:** Privacy 기본값을 "프롬프트 미수집"으로 두고, 수집 없이 성립하는 시나리오만으로 1차 출시한다

**가설 4 — 유닛 이코노믹스 및 지불 의사 가설**

> 수집 원가를 감당하면서 가격이 성립한다.

- **검증 방법:** 개발자 1인당 일일 이벤트·바이트를 Privacy 정책 ON / OFF 두 경우로 나눠 측정 → 좌석당 원가 원화 확정 / 3~5곳 유료 파일럿 LOI / 가격 앵커 A·B 테스트
- **성공 기준:** 좌석당 원가가 가격의 30% 이하 + 서명 2건 이상
- **측정 시 유의:** 데몬이 로컬 집계를 먼저 하므로 도구가 뿜는 원본 이벤트 수와 서버가 받는 양이 다르다. 두 지점을 각각 재야 엣지 집계의 효과가 숫자로 나온다
- **실패 시:** Privacy 기본값 · 샘플링 · 보존 기간을 가격표의 변수로 삼는다

### 5-2. 착수 전 결정이 필요한 항목

| # | 열린 이슈 | 막히는 것 |
| --- | --- | --- |
| 1 | 정책 Manifest 재조회 방식 — 현재 설치 등록 시 1회 수신으로 고정돼 정책을 바꿔도 기존 설치에 반영되지 않는다 | Policies 화면이 "바꿔도 안 먹는 설정"이 된다. 마스킹 규칙 변경이 특히 위험 |
| 2 | 서버 Masker의 정책 참조 방식 — 파이프라인이 조직별 정책을 어떻게 읽는가 (직접 조회 · 캐시 · 발행 시 푸시) | 정책 기반 마스킹 구현 전체 |
| 3 | 감사 로그 — 저장 대상·저장소 미정. 관측성 로그로 대체됐다고 보지 않는다 | 보안 심사(가설 3) |
| 4 | 실패 Signal 식별 방식 — 실패 마커 · 배치 키 · 재처리 대상 선택 기준 | 복구 절차를 아직 구현할 수 없다 |
| 5 | Provider 공시 단가표의 소유·갱신 주체와 저장 위치 — 코드 상수 · 설정 · DB 중 무엇인가, 단가 개정 시 소급 정정을 어떻게 발동하는가 | 금액 정확도 전체. 제품 원칙 3의 전제 |
| 6 | Self-hosted 배포의 구성 차이와 관측성 대체 경로 — 사내망에서 CloudWatch · Sentry를 쓸 수 없다 | 대기업·폐쇄망 세그먼트 전체 |
| 7 | 배포 아티팩트 저장소 — 클라이언트 바이너리·설치 스크립트를 둘 곳 | 설치 온보딩 착수 |
| 8 | 경계 auth 계층의 배치 — 애플리케이션 서버 안인가 별도 서버인가 | Gateway 구성 |
| 9 | 시나리오 카탈로그의 개수와 카테고리별 배분, `설정 필요` 시나리오가 연결할 설정 화면 매핑 | 시나리오 런처의 실제 내용물 |
| 10 | Overview 위젯 범위 — 후보 중 이상 탐지·알림은 이후 과제와 중복 | 첫 화면의 구성 |

3번과 6번 없이는 보안 심사에 들어가지 않는다. 5번 없이는 금액을 약속하지 않는다. 가설 2의 Codex 매핑 없이는 도구 횡단을 피치덱에 쓰지 않는다.

### 5-3. 4주 로드맵

1. **(1주차)** 자체 팀 수집 활성화 → 이벤트 볼륨·원가 측정 시작(Privacy ON/OFF 양쪽) / Codex 시그널 매핑 착수 / 기본 마스킹 룰셋 초안
2. **(1~2주차)** Wizard of Oz 대상 5개사 섭외 및 수작업 리포트 발송 / 정보보안 담당 3인 인터뷰(부록 A 흐름도 지참)
3. **(2주차)** §5-2 중 3 · 5 · 6번 우선 결정
4. **(3주차)** 가격표 · 약속 범위 · Privacy 기본값 확정 / 시나리오 카탈로그 초기 목록 확정
5. **(4주차)** §1-1의 세 갈래(글로벌 / 범위 확장 / 부트스트랩) 중 하나를 선택해 문서에 명기

### 5-4. 프로토타입 단계에서 검증할 핵심 질문

- [ ] 리포트를 받고 실제로 조치했는가? (가설 1의 유일한 성공 지표)
- [ ] 관리자가 실제로 던진 질문은 무엇이었는가? 카테고리 8종으로 다 담기는가, 빠진 카테고리가 있는가
- [ ] 시나리오를 골랐을 때 도착한 화면이 답을 담고 있었는가, 아니면 한 번 더 필터를 만져야 했는가
- [ ] `설정 필요` 배지를 봤을 때 실제로 설정하러 갔는가, 아니면 거기서 이탈했는가
- [ ] 공시 단가 기준 금액과 계약 적용 금액을 나란히 보여줬을 때 헷갈리지 않았는가? 어느 쪽을 "우리 비용"으로 인식하는가
- [ ] 계약 단가 입력을 누가 알고 있고 누가 입력하는가? 재무팀인가 CTO인가
- [ ] 도구 2종을 한 화면에서 보는 것이 수기 합산 대비 얼마나 시간을 아끼는가?
- [ ] 팀별 집계 결과를 그대로 내부 보고에 쓸 수 있는가? 프로젝트 축이 없어서 막히는가
- [ ] 마스킹 규칙을 직접 정할 수 있다는 것이 보안 심사에서 실제로 작동하는 논리인가
- [ ] 마스킹 완료본을 재처리 목적으로 보관하는 것을 어떻게 받아들이는가? 허용 보존 기간은
- [ ] 설치를 몇 분 만에 끝냈는가? 실패했다면 어느 단계에서인가
- [ ] 미설치자에게 누가 어떻게 독촉하는가? 그 절차가 조직에 실재하는가
