# 0024. dev 시드의 지연 감시는 왕복 시간과 HTTP 응답 요약 시간을 구분한다

## Status

Accepted — [ADR 0023](0023-dev-historical-dashboard-dataset.md)의 지연 중단 조건에 명시적으로 선택하는 측정 방식을 추가한다. 기존 기준도 유효하며, 실행별로 측정 방식과 상한을 고정하고 적용 확인을 기록한다.

## Context

`pulsemetry-backend`의 과거 시드 도구는 `infra`가 공급한 dev 데이터베이스를 제한 속도로 사용한다. ADR 0023은 기준 조회 지연의 두 배, 메모리 압박, 오류 또는 오래된 지표가 관측되면 다음 작업을 중단하도록 정한다.

운영자가 AWS 터널을 통해 측정하는 전체 왕복 시간에는 서버 밖의 전송·대기·로컬 스케줄링이 포함된다. 같은 메타데이터 조회를 다섯 번 측정한 중앙값이 중단선을 넘은 두 구간에서, 대응하는 서버 query log의 실행 시간은 각각 1~2ms였다. 해당 시간 범위의 다른 완료·실패 쿼리 기록, 서버 오류와 메모리 압박 증가는 관측되지 않았다. 이 증거만으로 특정 전송 구간을 원인으로 확정할 수는 없다.

ClickHouse 24.8의 `X-ClickHouse-Summary.elapsed_ns`는 HTTP 응답 버퍼가 요약 헤더를 작성하기 전까지 누적한 시간이다. `wait_end_of_query=1`로 짧은 결과를 버퍼링하면 쿼리와 결과 버퍼링이 끝난 뒤 요약을 받는다. 이 값은 순수 SQL·CPU 시간이나 query log의 `query_duration_ms`와 동일하지 않으며, 최종 응답 본문의 전송과 전체 왕복 시간을 포함하지 않는다.

## Decision

- 기존 대상 설정은 왕복 지연과 기존 baseline 두 배 조건을 그대로 사용한다. 다른 측정 방식으로 자동 전환하지 않는다.
- 새 방식은 실행 대상 설정에서 명시적으로 선택하고 고정 상한을 선언한다. 설정과 해시는 실행 기록에 보존한다. 관측 파일의 방식·상한이 대상 설정과 다르면 거부한다.
- 새 방식은 동일한 `system.parts` 메타데이터 조회 다섯 번의 HTTP 응답 요약 시간을 사용한다. `wait_end_of_query=1`, `send_progress_in_http_headers=0`을 명시한다. 각 요청의 전체 왕복 시간도 별도로 보존한다.
- 각 요청은 정상 상태 코드·예상한 작은 결과·정확히 하나의 유효한 요약 헤더를 확인한다. 누락·중복·잘못된 JSON·0 이하 또는 유한하지 않은 elapsed, HTTP 오류·본문 오류·timeout은 그 즉시 중단한다. 실패를 중앙값으로 제외하지 않는다.
- 성공한 다섯 원시 값과 원시 값으로 재계산한 중앙값이 일치해야 한다. 서버 응답 요약 시간의 중앙값이 고정 상한 이상이면 중단한다. 요청 시작 간격은 최소 0.2초이며 각 요청 전후의 자원·identity·오류 검사와 원래 관측 시각 기준 40초 유효성을 유지한다.
- 전체 왕복 시간은 새 방식에서 지연 상한 판정에 사용하지 않고 진단값으로 보존한다. HTTP 요청 실패·timeout은 계속 중단 사유다. 기존 왕복 지연 baseline을 서버 응답 요약 시간의 baseline으로 표시하지 않는다.
- 메모리 working set 75%, 실행 전 압박 카운터와 container identity, INSERT·조회 오류, 데이터 해시·중복 대조, 속도 제한과 SSO 활성화 순서는 바꾸지 않는다. 기존 중단 기록은 보존하며 정상 표본만으로 자동 해제하지 않는다.

## Constraints

이번 soma 검토안의 고정 상한은 **58.816084000000046ms**다. 이전 왕복 지연 중단선의 숫자를 유지한 새로운 의미의 상한이며, 새 서버 baseline을 측정하거나 그 두 배를 계산한 값이 아니다. 측정 방식이 달라지므로 기존 승인과 동등하다고 간주하지 않는다.

새 방식으로 dev를 재개하려면 로컬 검증 결과와 제외되는 지연 구간을 사용자에게 제시하고 명시적인 적용 확인을 받아 실행 기록에 연결한다. 원래 manifest·데이터·중단 기록은 보존하고 새 대상 설정·도구 버전·실행 상태의 변경 근거를 기록한다. 로그 삭제, 기준 상향, 계정 비밀번호 변경은 이 제안에 포함하지 않는다.

## Alternatives Considered

### 왕복 시간의 중앙값과 기존 중단선을 유지한다

서버 밖 지연까지 보호 조건으로 유지하지만, 서버 부하와 무관한 것으로 보이는 지연에도 긴 검증이 반복 중단될 수 있다. 기존 실행의 유효한 선택지로 남긴다.

### 왕복 시간의 중단선을 높인다

구현은 작지만 관측된 실패에 맞춰 숫자를 높이면 허용 가능한 서버 부하와의 관계가 불명확하다. 이번 제안은 이 대안을 채택하지 않는다.

### query log의 실행 시간으로 판단한다

서버 기록과 대조하기에는 유용하지만 비동기 로그 발행을 기다려야 하며 현재 요청의 즉시 중단 판정에 사용하기 어렵다. 사후 진단 근거로 사용한다.

## Consequences/Tradeoffs

### Positive

- 서버가 기록한 HTTP 응답 준비 구간과 전체 왕복 구간을 분리해 판단하고 원시 증거를 함께 남긴다.
- 대상 설정의 명시적인 선택과 해시로 측정 의미의 암묵적인 변경을 막는다.
- 기존 실행과 데이터 처리 로직을 유지하면서 새 기준의 실패 경계를 독립적으로 시험할 수 있다.

### Negative

- 새 기준은 전체 왕복 지연, 서버 응답 버퍼가 만들어지기 전의 대기와 최종 본문 전송을 모두 감시하는 지표가 아니다. 전체 서비스 지연이나 API의 정상 동작을 보장하지 않는다.
- 고정 상한의 적절성은 별도의 운영 판단이다. 기존 숫자와 같다는 이유만으로 안전성이 동등하다고 주장할 수 없다.
- ClickHouse HTTP 요약의 의미와 헤더 발행 조건에 의존한다. 다른 버전·프록시·전송 설정에서는 계약을 다시 확인해야 한다.

## Acceptance Criteria

- 기존 왕복 지연 방식의 회귀 테스트가 통과한다. 미지정 대상이 새 방식의 관측을 받아들이거나, 새 방식이 기존 필드를 무시하는 경로가 없다.
- 유효한 요약과 원시 다섯 값, 상한 경계, 요청 오류, 요약 누락·중복·잘못된 값, 노후 지표와 메모리 압박의 중단을 검증한다.
- 동일한 1 CPU·2GiB 로컬 환경에서 기존 193배치의 전체 대조와 7분 이상 관측을 수행한다. 원래 상태 파일·기준·압박 이력은 보존하고 새 대상 설정을 쓴 검증용 상태와 구분한다.
- 데이터 조회·삽입·직렬화 로직이 변경되지 않았음을 확인한다. 재검증 후 신규 데이터 행과 ACK는 증가하지 않는다.
- dev 적용 확인을 기록하기 전에는 기존 중단을 해제하거나 SSO를 활성화하지 않는다.
