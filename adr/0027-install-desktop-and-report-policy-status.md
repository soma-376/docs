# 0027. 설치 과정에서 데스크톱 앱을 함께 설치하고 정책 적용 상태를 표시한다

## Status

Accepted

## Context

`pulsemetry-backend`의 부트스트랩은 CLI만 설치한다. `telemetryctl`의 GUI는 별도 패키지이며
정책 정보가 예시 데이터다. 설치 완료 후 앱을 열고 실제 적용 정책과 서버 정책의 차이를
확인하려면 두 저장소의 설치·다운로드 계약이 함께 바뀌어야 한다.

## Decision

- 부트스트랩은 등록 성공 후 `pulsemetry gui install`을 실행한다. CLI가 등록 서버에서
  현재 OS·CPU의 GUI 패키지를 받아 사용자 디렉터리에 설치한다. 관리자 권한을 요구하지 않는다.
- 기존 CLI 다운로드 이름은 유지하고 GUI 여섯 이름을 허용 목록에 추가한다.
  서버는 같은 릴리스 선택·SHA256SUMS 검증을 적용한다. 다운로드 표시 이름은 `Pulsemetry`다.
- 이미 설치된 GUI를 덮어쓰지 않는다. 데몬 준비 완료를 확인한 뒤 처음 한 번 연다.
  성공한 실행 요청만 기록한다. 재실행은 단일 인스턴스의 기존 창을 표시한다.
  GUI 설치·실행 실패나 데스크톱 세션 부재는 등록·데몬·수집 성공을 취소하지 않는다.
- heartbeat 응답의 `expected_config_revision`을 데몬이 적용한 `config_revision`과 비교한다.
  결과·확인 시각과 적용 manifest의 수집 항목을 인증된 로컬 API로 GUI에 제공한다.
  더 큰 판은 업데이트 대기, 같은 판은 적용 완료, 확인 전·실패·오래된 결과는 따로 표시한다.
- GUI는 설치 토큰을 읽거나 서버에 직접 접근하지 않는다. heartbeat는 즉시·매분 독립 실행한다.
  정책 감지는 manifest 재조회·토큰 회전·정책 자동 적용을 수행하지 않는다.
- PRD의 GUI 제외 범위를 개정해 설치·개인 사용량·정책 상태 표시를 포함한다.

## Alternatives Considered

### A. 데몬이 시작할 때마다 GUI를 연다
- 장점: 설치 코드가 짧다.
- 단점: 로그인·장애 복구 때 창이 반복해서 뜨고 수집 서비스가 데스크톱 세션에 의존한다.
- 탈락 이유: 최초 설치 완료 시에만 창을 열어야 한다.

### B. GUI가 서버에서 정책을 직접 조회한다
- 장점: 데몬의 조회 API를 늘리지 않는다.
- 단점: 설치 자격증명 접근이 퍼지고 실제 집행 버전과 표시가 갈릴 수 있다.
- 탈락 이유: 정책 집행자인 데몬의 상태를 표시한다.

## Consequences/Tradeoffs

### Positive
- 설치 후 개인 화면과 실제 적용 정책을 바로 확인한다.
- 확인 실패를 최신 정책 적용 완료로 오인하지 않는다.

### Negative
- 서버 배포 디렉터리에 GUI 패키지도 공급해야 한다. 다운로드 용량이 늘어난다.
- OS별 설치·실행 검증이 필요하다. GUI 자동 업데이트와 정책 자동 적용은 포함하지 않는다.
- 서버 보고 기능이 꺼져 있으면 서버 최신 판은 확인 실패로 표시한다.
