# 0030. 설치 보고 공백과 보고된 전송 손실을 분리해 표시한다

## Status

Accepted

## Context

`pulsemetry-backend`의 최신 설치 보고와 합쳐진 수집 구간은 현재 상태를 판정하지만,
누적 손실이 서버에서 언제 확인됐는지는 복원하지 못한다. 보고가 없다는 사실도 전송 손실의 증거는 아니다.
`pulsemetry-frontend`의 헤더·알림함, backend의 보고 저장·평가·조회, `infra`의 원천 읽기 권한과
`telemetryctl`의 기존 누적 카운터 계약을 함께 맞춰야 한다.

## Decision

### 보고 공백

활성 설치의 마지막 heartbeat 서버 수신 시각부터 168시간 이상 지나면 `collection` 범주의
시스템 규칙 `installation_report_gap`을 평가한다. 최초 미보고 설치는 등록 시각을 기준으로 한다.
조직별 설정 없이 항상 평가하며 폐기 설치는 새 사건을 만들지 않는다. 사건 키는 조직·설치 ID·기준 시각이다.
같은 기준의 반복 평가는 같은 사건이다. 새 보고로 기준이 바뀌면 이전 사건을 해소하고, 새 기준도
이미 168시간을 넘겼으면 새 사건을 만든다. 폐기는 별도 사유로 열린 사건을 종료한다.

기존 주기 평가의 다음 성공 회차에 반영한다. 평가 중단 중 발생했다가 이미 해소된 공백은 사후 복원하지 않는다.
`resolutionDetectedAt`은 평가기가 해소를 확인한 시각이며 최초 복구 시각이나 마지막 보고 시각이 아니다.
확인 여부는 해소 여부와 독립이다. 해소가 자동 확인을 만들지 않으며 재발 사건은 이전 확인을 승계하지 않는다.
공백의 `eventCount`는 null이다.

### 보고된 손실

손실은 데몬이 보고한 페이로드 수다. 사용 이벤트·토큰 수, 전송 대기, 정책상 비수집, 단순 보고 공백을 포함하지 않는다.
`mode=local && forwarding=true`인 보고만 관측 근거로 삼으며 수신기 가동 시각은 추가 조건이 아니다.
같은 실행의 최고 누적 손실값을 기준으로 양수 증가분만 원장에 저장한다. 새 실행의 기준값은 0이다.
같은 실행에서 값이 감소해도 최고값은 낮추지 않고 집계 제한을 기록한다. `delivered` 감소나 `pending` 증가는 손실이 아니다.
카운터 초기화에는 기존 `run_id` 규약에 따라 새 실행 ID를 쓴다.

집계 창은 서버 기준 `[windowEnd − 168시간, windowEnd)`다. 증가분의 서버 확인 시각으로 집계하며
분석 날짜·팀·벤더 필터를 적용하지 않는다. 설치 폐기·모드 변경 후에도 이미 기록한 최근 손실은 남긴다.
실행별 커서는 창이 지났다는 이유로 지우지 않는다. 증가분 원장은 기존 보고 보존 정책을 따르되 최소 168시간을 보장한다.

전환 시 구 writer 종료를 보장하고 추적 시작 시각을 기록한다. 최신 heartbeat는 기준값으로만 이관하고,
보존된 과거 실행 ID는 과거 실행으로 표시하여 재합산을 막는다. 과거 구간 손실의 비례 배분·종료 시각 백필은 하지 않는다.
삭제된 과거 실행의 임의 재생을 식별한다고 보장하지 않는다. 구 writer로 되돌릴 때는 추적 중단을 기록하고
다시 시작할 때 기준값과 집계 가능 시작을 재설정한다.

### 가용성과 화면

`complete`는 기간의 보고된 증가분을 집계할 근거가 갖춰졌음을 뜻하며 모든 실제 전송의 무손실 보장이 아니다.
`partial`은 추적 시작·중단·카운터 감소 등 제한과 확인된 수량을 함께 반환한다.
`unavailable`은 집계 기반·관측 근거가 없거나 조회 실패한 상태이며 수량은 null이다.
단순 보고 공백은 집계 가용성을 낮추지 않는다. ClickHouse 장애는 독립적인 RDS 손실 조회를 덮어쓰지 않는다.

헤더는 “최근 7일 보고된 전송 손실 N건”을 표시하고 부분 집계의 시작 시각·제한을 함께 알린다.
집계 불가는 “최근 7일 전송 손실 집계 불가”, 구버전 응답의 필드 부재는 “집계 정보 없음”이다.
재조회 실패 시 기존 값과 기준 시각을 보존하고 갱신 실패를 표시한다. 영향 기기는 같은 창으로 페이지 조회하며 폐기 상태도 보여준다.
공백 알림의 지속·해소와 미확인·확인함은 각각 표시한다. 공통 알림 수에는 포함하고 보안 전용 목록에서는 제외한다.

### 호환 배포

새 범주·evidence를 수용하는 프론트를 먼저 배포한다. 구 enrollment writer를 종료한 후 이관하고 신규 writer를 시작한다.
신규 조회 테이블에 대한 최소 SELECT 권한을 확인한 뒤 dashboard를 배포한다. 미래 테이블 전체 grant나 앱 기동 시 자동 grant는 하지 않는다.
사용자용 활성화 토글과 신규 알림 채널은 추가하지 않는다. 사용량·금액·기간 완전성 재설계는 이 결정의 범위가 아니다.

## Alternatives Considered

### A. 보고 공백을 손실로 계산한다

실제 전송 여부와 손실량을 알 수 없으므로 수량을 지어내게 된다. 공백은 별도의 상태 사건으로 남긴다.

### B. 기존 구간의 누계를 7일로 나눠 넣는다

손실 관측 시각을 복원할 수 없고 전환 직후 과거 누적값을 신규 손실로 표시한다. 증가분 원장을 사용한다.

## Consequences/Tradeoffs

### Positive

보고 부재와 명시적 손실이 구분되고 재보고·카운터 감소가 손실을 중복 합산하지 않는다.
확인과 해소의 독립성으로 관리자의 조치 기록과 시스템 상태를 함께 유지한다.

### Negative

실행별 커서가 장기 보존되며 증가분·제한 이력 저장과 읽기 권한이 추가된다.
초기 7일은 부분 집계이고 중단 중 이미 복구된 공백·삭제된 실행의 재생은 복원할 수 없다.
배포 때 구 writer 종료와 중단 기록을 운영 절차로 보장해야 한다.
