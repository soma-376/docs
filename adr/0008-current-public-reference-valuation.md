# 0008. 사용 환산액은 버전을 고정한 참조 단가로 평가한다.

## Status

Accepted

## Context

- PRD 제품 원칙 3은 금액을 공시 단가 기준 금액과 조직 계약 단가 적용 금액으로 나눈다. PRD §8-5는 단가표의
  소유·갱신 주체와 저장 위치, 단가 개정 시 소급 정정 방식을 미결로 남겼다.
- backend ADR 0020은 검증된 불변 가격 프로파일로만 추정 비용을 허용하고, 기존 가격 단계는 사건 시각에 유효한 요금만 고른다.
- 공급자 공식 문서로 단가를 확인할 수 있는 모델은 일부다. Codex 자동 검토(`codex-auto-review`)처럼 공개 단가가 없는
  모델도 실제 사용량에 섞여 있다.
- Claude 캐시 생성은 TTL(5분·1시간)에 따라 단가가 다르지만 텔레메트리에 TTL이 없다.
- 이 결정은 backend(가격 계산·적재·재평가)와 frontend(환산액 해석·표시)에 걸린다.

## Decision

1. 사용 환산액은 버전을 고정한 참조 단가표로 계산한 Standard/global/USD 텍스트 토큰 평가 금액이다. 제품 원칙 3의
   "공시 단가 기준 금액"은 이 값이다. 실제 청구액·구독 금액·조직 계약액·벤더 보고 금액이 아니며, 그 값들과 섞지 않는다.
2. 참조 단가표는 backend가 버전으로 관리한다. 출처는 두 가지다.
   - 공급자 공식 문서로 직접 확인한 모델 단가. 이 값이 우선한다.
   - Codeburn 0.9.24의 고정 카탈로그(번들·보완 가격표와 명시적 별칭). 실행 중 조회하지 않고, 파일 해시·원본 버전·
     제외 범위를 기록한다.

   별칭(예: `codex-auto-review → gpt-5.5`)은 환산 기준의 선택이다. 모델 동일성이나 실제 청구액을 확인했다는 뜻이 아니며,
   원본 모델 ID는 바꾸지 않는다.
3. 가격은 단가표에 고정된 기준 시각으로 고른다. 사건 시각에 현재 요금이 유효했다고 표시하지 않는다.
4. 토큰 의미가 검증된 사용량만 계산한다. 의미 프로파일이 서로 다르면 같은 비중복 성분(`input_uncached`·`output`·
   `cache_read`·`cache_create`)으로 검증된 호환 집합만 합산한다. 초기 호환 집합은 `claude-code-exclusive-v1`과
   `codex-responses-inclusive-v1`이다.
5. Claude 캐시 생성은 5분 쓰기 단가로 평가한다. 평가 기준일 뿐 실제 TTL 판정이 아니다. 명시 0은 0, 미보고는 null이다.
6. 공식 단가에 요청 길이별 요율이 있으면 그 요청의 입력 토큰 수로 구간을 고른다. 여러 요청의 누계를 한 요청으로 보지 않는다.
7. 단가표에 없는 모델, 검증되지 않은 토큰 의미, 필요한 성분의 누락은 null이다. 미가격을 0원으로 만들거나 다른 모델의
   단가로 추정하지 않는다.
8. 단가표는 불변이다. 개정은 새 `pricing_version`을 만든다. 저장된 사용량은 자동으로 다시 계산되지 않는다.
9. 저장된 사용량의 재평가는 입력과 범위를 고정한 내부 운영 작업이다.
   - 토큰 의미가 확인된 행은 가격만 다시 계산한다. 관측 ID·날짜·토큰·모델·소속·원본 참조는 보존한다.
   - 의미가 없는 행은 원본이 남아 있을 때만 원본 재정규화로 고친다.
   - 원본도 없는 행은 복구 불가로 사유와 건수를 남긴다. 추정으로 채우지 않는다.
   - 대시보드는 재평가 뒤 새 snapshot에서 값을 읽는다.

## Alternatives Considered

### A. 공급자 공식 문서로 확인한 모델만 계산한다
- 장점: 모든 단가에 공식 출처가 있다.
- 단점: 자동 검토 등 실제 사용량의 상당 부분이 계속 미확인으로 남는다.
- 탈락 이유: 같은 기준으로 사용량을 비교한다는 지표 목적을 채우지 못한다. 공식 확인 단가는 우선 적용으로 유지한다.

### B. 사건 시각에 현재 요금을 소급 적용한다
- 장점: 기존 사건 시각 가격 경로를 그대로 쓴다.
- 단점: 과거 가격의 증거를 꾸민다.
- 탈락 이유: 참조 기준 평가와 과거 요금을 구분할 수 없다.

### C. TTL을 모르는 캐시 생성은 계속 null로 둔다
- 장점: 실제 청구 추정에 보수적이다.
- 단점: 캐시 생성량이 알려져 있어도 환산액을 보여줄 수 없다.
- 탈락 이유: 고정 기준으로 사용량을 비교하는 지표라 평가 기준을 명시하면 충분하다.

### D. 벤더 보고 비용으로 빈 환산액을 채운다
- 장점: 미확인 건수가 줄어든다.
- 단점: 성격이 다른 금액을 섞는다.
- 탈락 이유: 보고 비용과 환산액은 계속 별개다.

## Consequences/Tradeoffs

### Positive

- 넓은 모델 범위를 같은 기준으로 비교하고, 같은 단가표로 결과를 재현한다.
- 원천 시각·토큰·모델을 보존하고 모르는 값은 null로 남긴다.

### Negative

- 환산액은 실제 청구액과 다르다. 화면과 CSV에서 이 구분을 유지해야 한다.
- Codeburn 값과 별칭은 참조 기준이라 실제 사용 모델·과금을 증명하지 않는다.
- 원본이 없는 의미 미검증 사용량은 계속 미확인으로 남는다.
- 단가 개정과 재평가는 명시적인 버전·운영 작업이 필요하다.

## Acceptance Criteria

- 같은 입력과 단가표는 같은 Decimal 금액을 만든다.
- 직접 확인한 모델의 단가와 요청 길이 경계, Codeburn 카탈로그와의 대조, 미등록·미검증·누락의 null을 검증한다.
- 캐시 생성 0·양수·누락을 각각 검증한다.
- 재평가는 쓰기 중단 뒤 같은 입력으로 이어지고, 다시 실행하면 쓰기가 0건이며, 의미·원본이 없는 행은 바뀌지 않는다.

## Follow-up

- 단가표 갱신 주기와 담당을 정한다.
- 운영 데이터 재평가의 실행 승인 주체를 정한다.
- 원본 재정규화 경로를 만든다(backend).
- 저장소에 고정한 Codeburn 카탈로그의 재배포 조건을 확인한다.
