# 0023. dev 과거 시드는 독립 파일과 제한 속도로 적재하고 검증 후 SSO와 알림을 활성화한다

## Status

Accepted — PostgreSQL 조회 권한 복구, 측정에 근거한 ClickHouse 튜닝, soma 적재와 SSO 연결은 각각 검토 가능한 변경으로 관리한다. 로컬 성공 결과를 확인한 사용자의 dev 적용 승인을 실행 기록에 보존한다.

## Context

backend의 화면용 과거 시드는 infra가 운영하는 PostgreSQL·ClickHouse와 로그인 설정에 걸친다. 조직과 구성원이 과거에 가입하고 설치한 뒤 사용 이력이 쌓인 상태를 재현해야 한다. 기존 Compose 초기화 명령의 접속 주소만 dev로 바꾸면 스키마·인증 키·기존 데이터까지 초기화할 수 있다.

dashboard의 알림 평가는 조직의 SSO 활성 여부와 별개로 활성 규칙을 읽는다. PostgreSQL에 완료된 수집 구간과 활성 규칙을 먼저 넣으면 ClickHouse 적재 도중 불완전한 데이터로 평가와 snapshot 생성이 시작될 수 있다.

ClickHouse의 snapshot 읽기량에는 원천과 materialized view의 누적 처리가 포함된다. 읽기 바이트, 결과 바이트, 쿼리 메모리와 컨테이너 메모리는 같은 지표가 아니다. working set이 낮아도 파일 캐시를 포함한 cgroup 메모리가 상한에 닿을 수 있으므로 둘을 함께 관측해야 한다.

## Decision

### 독립 생성과 직접 적재 경계

- 기존 로컬 Compose의 초기화·적재·reset 제한을 유지한다. 별도 도구만 명시적인 local/dev 대상으로 과거 데이터를 적재하며 prod, 자동 DB 마이그레이션과 기존 조직 초기화를 지원하지 않는다.
- soma는 고유 데이터셋 ID와 환경별 UUID 영역을 사용한다. 기존 조직 이름·slug·ID가 충돌하면 덮어쓰지 않고 중단한다.
- 50팀·활성 회원 400명(owner 1명, admin 1명, 일반 구성원 398명)·설치 398개를 생성한다. 팀별 인원은 20명 팀 5개, 12명 팀 10개, 8명 팀 15개, 3명 팀 20개다.
- 실행 시각을 고정하고 KST 기준 전날까지 완료된 180일을 생성한다. 가입·설치는 첫 사용보다 앞서며, 주말을 포함한 모든 날짜·팀 조합에 최소 한 세션을 보장한다. 각 설치의 수집 구간은 마지막 날 종료와 서버 확정 대기 10분까지 덮고 미래 시각을 생성하지 않는다. 고정 실행 시각은 KST 00:10 이후여야 하며, 이 경계를 만족하지 않는 입력은 거부한다.
- 원래 풍부한 사용량을 유지한다. 조회 한도를 맞추려고 사용량을 자동 축소하지 않는다. 생성·파일 출력·해시·검증은 월별 또는 더 작은 단위로 처리한다.
- manifest는 환경·설정·기간·고정 시각·조직 ID·행 수·파일 및 배치 해시를 고정한다. 재개 시 재생성하지 않고 같은 파일을 사용한다.
- PostgreSQL에는 조직·회원·팀·설치·정책·수집 근거를, ClickHouse에는 사용 이벤트와 수신 원장을 입력한다. 캐시는 실제 대시보드 조회가 생성한다. 직접 적재한 합성 데이터는 실제 OTLP 파이프라인 성공이나 청구액의 증거가 아니다.

### 적재·재개·활성화

- 신규 PostgreSQL 데이터는 조직 SSO와 모든 시드 알림 규칙을 비활성 상태로 한 트랜잭션에 준비한다. 규칙의 원래 활성 값·ID·버전은 manifest에 보존한다. 기존 앱은 적재 중에도 실행한다.
- ClickHouse는 최대 2,000행 또는 JSON 4MiB, 동시 요청 1개, 동기 응답 뒤 1초 대기를 적용한다. 처음 5개 배치가 확인되면 30초 관찰한다.
- 대상 서버 identity·스키마·보존 경계·배포 이미지의 토큰 해석 계약·OIDC 연결과 실제 관측 지표를 사전 확인한다. plan 성공이 이 검증을 대신하지 않는다.
- 동일 컨테이너의 working set 75% 이상, 고정한 기준 조회 지연의 2배 이상, INSERT 오류·timeout 또는 지표 누락·노후화가 있으면 다음 작업을 중단한다. cgroup `memory.events.max`, `oom`, `oom_kill`이 실행 전 기준보다 증가해도 중단 기록을 남긴다. 컨테이너 identity 변경을 정상 counter reset으로 간주하지 않는다.
- 지표의 원래 관측 시각과 유효 기간을 보존한다. 감시는 이미 실행 중인 쿼리를 즉시 취소하는 장치가 아니다. 실패 기록을 지우거나 부하 중 기준값을 높여 자동 진행하지 않는다.
- 불확실한 배치는 서버 실행 종료를 확인한 뒤 ID와 내용으로 대조하고 없는 행만 보낸다. 내용이나 설정 해시가 다르면 중단한다. 전체 reset이나 무조건 재전송으로 복구하지 않는다.
- 검증 SELECT의 긴 ID 목록이 내부 query log에 반복 저장돼 적재 작업보다 큰 로그 병합 부하를 만들지 않도록, 해당 요청에만 SQL 기록 길이를 4,096바이트로 제한한다. 쿼리 로그를 끄거나 서버 전체 설정을 바꾸지 않는다. query ID·실행 시각·읽기량·메모리·오류 지표를 유지하고 실행 journal에 전체 SQL 해시·manifest 해시·배치·검증 범위를 남긴다. ID와 순서를 포함한 원본 배치 파일, 쿼리 생성 규칙과 직렬화가 담긴 실행 도구의 소스 및 SHA-256을 함께 보존하여 원문을 재구성하고 해시로 대조한다.
- 두 DB의 전체 대조와 부하 확인이 끝나면 한 PostgreSQL 트랜잭션에서 해당 조직의 SSO와 시드 알림 규칙의 원래 활성 값을 함께 반영한다. 규칙 버전·내용이 다르거나 상태가 혼합돼 있으면 중단한다. 활성화 응답 유실은 실제 상태와 checkpoint로 확인한다.
- 기존 Cognito 관리자 두 계정을 soma의 owner/admin으로 사전 등록하고 신규 `oidc_subject`는 비워 둔다. 최초 연결은 기존 인증 구현을 따른다. 조직에 설정한 issuer를 검증하고, 검증된 ID Token의 이메일이 로그인 힌트 및 조직 안의 유일한 사전 등록 회원 이메일과 일치할 때 subject를 연결한다. 연결 후에는 같은 조직·issuer·subject만 허용하며 다른 subject로 덮어쓰거나 중복 subject를 연결하지 않는다. 기존 비밀번호 변경이나 신규 인증 우회 경로를 만들지 않는다.

### 측정에 근거한 인프라 변경

- PostgreSQL 조회 권한 복구는 PROJ-262의 별도 도구·SQL·검증·복구 절차로 다룬다. 시더가 서비스 권한을 암묵적으로 넓히지 않는다.
- ClickHouse와 앱의 현재 실행 이미지·자원 조건을 로컬에서 재현한다. 배포 이미지의 내용, CPU·메모리·PVC, 원천 반환 결과 100,000행·10MiB, 조직별 snapshot 동시 생성 1개와 60초 제한을 유지한다. 조직별 동시성은 서버 전체 동시성 제한이 아니다.
- snapshot 복사 읽기 한도는 성공한 쿼리의 최대 `read_rows/read_bytes`에 1.5배를 곱하고 행은 10,000개, 바이트는 MiB 단위로 올림한다. 현재 검증값 602,733행·256,102,794바이트에 따른 한도는 910,000행·367MiB다. 이 값은 RAM 할당량이 아니다.
- `system.metric_log`의 `max_compress_block_size=65536`, `merge_max_block_size=512`를 기존 테이블과 동일한 서버 `metric_log.engine` 정의에 적용한다. 다른 engine 구조·수집 주기·버퍼·TTL·로그 보존은 바꾸지 않는다.
- 테이블 ALTER만으로 재시작 지속성을 보장하지 않는다. 실제 default table → ALTER → 동일 XML 재시작과 역복구에서 원래 UUID·기존 행의 hash가 유지돼야 한다. ALTER와 Helm 변경은 원자적이지 않으므로 중간 실패 시 다음 적재를 중단한다.
- 현재 실행 image digest를 고정하고, 단일 replica 재시작의 일시 조회·수집 중단을 명시한다. 복구 시 원래 테이블 override를 먼저 복원한 뒤 서버 정의를 복원하며 같은 이미지 내용을 유지한다. 로그 테이블이나 PVC를 삭제하지 않는다.

## Alternatives Considered

Compose 초기화의 원격 접속 허용은 파괴 범위를 넓히므로 채택하지 않는다. 적재 중 dashboard를 끄거나 SSO만 끄는 방식은 실제 dev 조건과 자동 평가 경계를 검증하지 못한다. 데이터를 축소하거나 조회 제한을 무제한으로 푸는 방식도 사용하지 않는다. 새로운 snapshot 저장 구조와 공개 API 변경은 별도 설계다.

## Consequences/Tradeoffs

### Positive

과거 사용량을 재현하면서 공유 dev의 부하를 제한한다. 권한·인프라·시드의 적용과 복구 범위가 분리되고, 부분 적재가 완료 데이터로 공개되는 것을 막는다. 재실행과 응답 유실을 데이터 대조로 처리한다.

### Negative

두 DB의 원자적 commit은 없으므로 파일과 checkpoint를 보존해야 한다. 읽기 한도 확대는 CPU·메모리·I/O 부담을 높일 수 있다. 작은 내부 로그 블록은 병합·압축 작업량을 늘릴 수 있으며 단일 replica 재시작은 서비스 중단을 동반할 수 있다. 로컬 단독 성공은 공유 dev의 모든 동시 부하를 보장하지 않는다.

합성 수집 이력은 살아 있는 데몬의 현재 수집 상태를 보장하지 않는다. 모의 OIDC 로그인은 실제 dev Cognito 로그인 검증을 대신하지 못한다. 메모리 상한 접촉, 회수 압박, OOM과 서비스 실패를 서로 구분해 보고한다.

## Acceptance Criteria

50팀·400명·398개 설치와 9,000개 날짜·팀 조합, 시간 순서, 수집 구간, 토큰·비용·세션을 생성 파일과 DB에서 대조한다. 7·28·90일 이전 기간 비교와 180일 전체 조회, 개요·팀·구성원·모델·설정 화면을 확인한다. API·화면이 제공하지 않는 개별 필드는 검증했다고 주장하지 않는다.

실제 중단·재개, 같은 파일 재실행, 기존 조직 보존, 메모리 압박·오래된 지표의 중단을 검증한다. 실제 dev의 두 관리자 로그인과 화면, 행 수·기간·파일 크기·적재 시간·관측 최대 메모리·조회 한도·오류 및 복구 기록을 남긴다.
