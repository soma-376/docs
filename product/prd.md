## 1. 한 줄 정의

Claude Code · Codex 등 개발 AI 도구의 사용량과 비용을 한곳에 모으고, 조직 → 팀 → 구성원 축으로 나눠 보며,
조직이 맺은 계약 단가로 실비용을 환산하고, 관리자가 답을 얻고 싶은 질문을 고르면 그 답이 있는 화면을 여는
**AI 개발도구 사용 통합·가시화 플랫폼**.

## 2. 제품 원칙

1. AI 사용을 막는 게 아니라, 안전하고 효율적으로 쓰도록 돕는다.
2. 프롬프트 수집 여부는 조직의 Privacy 정책이 정하고, 수집한 것은 마스킹 이후에만 저장한다.
   마스킹은 클라이언트 데몬과 서버 두 곳에서 집행한다.
3. 금액은 두 값으로 나뉜다 — **공시 단가 기준 금액**과 **조직 계약 단가 적용 금액**.
   두 값은 이름을 구분해 표시하고 섞지 않는다.
4. raw 정확 수집 → 표시 → 그다음 인사이트.

## 3. 문제 정의 (POV)

> 개발 조직의 AI 지출을 책임지는 CTO·플랫폼 리드는, 여러 도구에 흩어진 비용을 한 화면에 모으는 것조차
> 수작업이고, 모아도 팀 단위로 떨어지지 않으며 우리 계약 단가가 반영되지도 않고, 무엇을 봐야 할지조차
> 모르는 문제를 겪는다. 왜냐하면 그들이 진짜로 원하는 것은 더 많은 지표가 아니라, "우리 계약 기준으로
> 어느 팀이 얼마를 쓰는가"라는 자기 질문에서 출발해 그 답이 있는 화면으로 곧장 도착하는 경험이기 때문이다.

제품이 주는 것은 **질문에서 화면으로의 도달**이지 절감 권고가 아니다. 절감 권고는 효율 어드바이스 영역으로 남긴다.

## 4. 타깃

- 개발자 **100~1,000명** 규모.
- Claude Code와 Codex를 함께 쓰는 조직. 이 두 CLI가 데이터 원천이다.
- 팀 단위 원가 파악 요구가 있는 조직: SI·수탁개발·다계열사 그룹사. **약속하는 최소 집계 단위는 팀**이다(프로젝트 축은 이후 과제).
- 제외: 50명 미만(스프레드시트로 충분), 5,000명 이상(Jellyfish·Faros가 이미 진입).

## 6. MVP 범위

### 6-1. 만든다

| # | 기능 | 내용 |
|---|---|---|
| 1 | **도구 횡단 통합 대시보드** | Claude Code · Codex OTel 수집, 전사 총비용 Overview, 도구별·모델별 분해 |
| 2 | **조직 축 집계** | 조직 → 팀 → 구성원 3단계 드릴다운, 조직-팀-사원 매핑 화면, 전역 팀 필터 |
| 3 | **계약 단가 실비용** | AI Provider 계약 단가 입력. 공시 기준 금액은 적재 시 저장, 계약 적용 금액은 조회 시 계산. 두 값을 이름으로 구분해 표시 |
| 4 | **질문 기반 시나리오 런처** | 카테고리 8종, 지표 레지스트리, 조직별 가용성 3단계 판정, 프리셋 적용, `?scenario={id}` 링크 복원 |
| 5 | **수집·마스킹 정책** | Privacy(무엇을 수집할 것인가) / 마스킹 규칙(무엇을 가릴 것인가) 2화면 분리, Manifest 배포, 데몬 1차·서버 2차 이중 집행 |
| 6 | **설치 온보딩** | 초대 발송 → 설치 페이지(OS 감지) → `enroll` 자동 배선 → 자동 실행 등록. 구성원별 설치 상태로 커버리지 확인 |

**시나리오 런처 카테고리 8종** — 비용·예산 / 사용 패턴·리밋 / 도입·채택 / 생산성·역량 / 보안·컴플라이언스 / 품질·운영 / 거버넌스.
시나리오는 **네비게이션 보조**다. 지표를 해석하거나 조언하지 않고 새 지표를 만들지도 않는다.

### 6-2. 비기능 요건 (옵션이 아니다)

1. 수집 항목과 마스킹 규칙을 관리자가 제품 화면에서 직접 보고 바꿀 수 있다.
2. 마스킹은 데몬과 서버 두 곳에서 집행한다. 클라이언트 마스킹을 믿고 서버 방어선을 생략하지 않는다.
3. 마스킹을 마치기 전의 데이터는 어떤 서버 저장소에도 쓰지 않는다.
4. 자격증명(토큰 원문·해시)은 어떤 서버 저장소에도 남기지 않는다. 테넌트 귀속은 검증으로 얻은 파생 식별자로 한다.
5. 파이프라인 4단계는 예외 없이 작업 전후를 로깅한다. 로깅이 없으면 복구가 성립하지 않는다.
6. 온보딩 필수 산출물은 초대 발송과 설치 상태(커버리지) 확인 표면이다.
7. 재처리는 내부 운영 도구로만 트리거한다. 관리자 화면·API를 두지 않는다.

이 7개는 [`architecture/overview.md`](../architecture/overview.md)의 아키텍처 불변식 I-1~I-14와 짝을 이룬다.

### 6-3. Non-goals (지금 만들지 않는다)

- **어드바이스 엔진 / 인사이트 생성** — 시나리오 런처와 같은 것으로 취급하지 않는다. 대응 컴포넌트를 두지 않는다.
- **프로젝트 단위 집계**, **팀 간 비교 전용 화면**, **팀장 권한 분리** — 약속 단위는 팀까지다.
- **폭주 세션 조기 경보 / 예산 알림** — 지금은 사후 조회까지.
- **데몬 GUI** — 데이터 계층은 있으나 화면을 만들지 않는다.
- **감사 로그** — 저장 대상·저장소 미정. 관측성 로그는 감사 로그가 아니다.
- **MDM 일괄 배포**, **LLM 자유 질의**, **Cursor·Gemini CLI 등 그 밖의 도구 연동**.
- **섀도우 AI 탐지** — 벤더 Admin/Analytics API를 원장으로 수집하는 경로가 필요한데 데이터 원천이 OTel 단일 계층이다.

## 7. 성공 지표 (검증 가설)

| # | 가설 | 성공 기준 | 실패 시 |
|---|---|---|---|
| 1 | **인사이트** — 관리자는 무엇을 물어야 할지 모르고, 질문 목록을 주면 실제로 답을 찾아본다 | Wizard of Oz 리포트 5건 발송 후 2주 내 **실제 조치 3건 이상** | 시나리오 카탈로그의 전제가 무너진다 |
| 2 | **수집 가능성** — Claude Code와 Codex를 같은 스키마에 담을 수 있다 | Codex 시그널이 `Unmapped`를 벗어나 집계에 들어감 + 공통 스키마와 provider별 확장 스키마 초안 확정 | 통합 범위를 축소해 명시하고 도구 횡단을 차별점에서 내린다 |
| 3 | **정책** — 조직이 수집 범위와 마스킹 규칙을 직접 정하고 마스킹 이후에만 저장하는 구조로 보안 심사를 통과한다 | 보안 담당 3인 중 2인이 "심사에 올릴 수 있다" + 정형 식별자 마스킹 정탐률 90% 이상 + 허용 보존 기간 하한선 확보 | Privacy 기본값을 "프롬프트 미수집"으로 두고, 수집 없이 성립하는 시나리오만으로 1차 출시 |
| 4 | **유닛 이코노믹스** — 수집 원가를 감당하면서 가격이 성립한다 | 좌석당 원가가 가격의 30% 이하 + 유료 파일럿 LOI 2건 이상 | Privacy 기본값·샘플링·보존 기간을 가격표의 변수로 삼는다 |

가설 1의 유일한 성공 지표는 "리포트를 받고 실제로 조치했는가"다. "흥미롭네요" 이후 아무 일도 없으면 실패다.
가설 4를 측정할 때는 **도구가 뿜는 원본 이벤트 수와 서버가 받는 양을 각각 재야** 데몬 로컬 집계의 효과가 숫자로 나온다.
